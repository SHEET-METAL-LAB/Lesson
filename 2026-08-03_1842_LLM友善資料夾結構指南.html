01 — 核心觀念

唯一真正稀缺的資源是 context

LLM 每一次回答，都只看得見「當下被載入的那些字」。整理資料夾的目的不是好看， 是決定哪些知識屬於每次都要看、哪些屬於需要時才去翻。

常駐層（Always-on）

每個新對話都會被自動讀進去。空間極貴，只放「模型自己推導不出來、而且弄錯代價很高」的東西： 本機環境陷阱、專案硬規則、命名慣例、檢查清單。

CLAUDE.md · MEMORY.md
按需層（Lazy）

只在相關時才被打開。長篇規範、歷史決策、除錯案例、任務計畫都放這裡。 容量幾乎無限，代價是「必須有一條指得到它的線索」。

.develop/ · .agent/directives/ · memory/*.md
機制層（Enforced）

寫在文件裡的規則會被遺忘，寫成測試或 hook 的規則不會。把重複踩到的坑 升級成「會變紅燈的東西」，是唯一能停止復發的作法。

tests/ · .claude/agents/ · settings.json
判準：一句話決定放哪一層 「如果模型不知道這件事，會出什麼錯？」錯得很貴又很難察覺 → 常駐。 錯了會立刻被編譯器／測試抓到 → 不必寫。介於中間、只在特定任務相關 → 按需層，並在常駐層留一行指標。
02 — 階梯

四層 CLAUDE.md：每層只回答一種問題

同名檔案放在不同深度，職責完全不同。上層講「所有專案都適用」，越往下越具體， 子目錄只講「這個資料夾裡的程式碼怎麼寫」。層與層之間是加疊不是覆寫；真要覆寫必須標註理由。

04 — 分工表

每一種檔案回答哪一種問題

最常見的失敗不是「沒寫文件」，而是同一件事寫在三個地方且互相矛盾。 下表是刻意設計過的職責邊界。

檔案／目錄回答的問題載入時機不該放什麼
~/.claude/CLAUDE.md「在這台機器上工作要注意什麼？」每個 session任何專案的具體細節
專案 CLAUDE.md「這個專案的規則是什麼？」進入專案可以從程式碼直接讀出來的事實
子目錄 CLAUDE.md「這層程式碼怎麼寫？」動到該目錄其他層的規範
CHANGELOG.md「這版改了什麼？」（對外）發版時過程、失敗嘗試、決策理由
.develop/<任務>/「當時為什麼這樣做？」（對內）接手相關工作常駐規則（那屬於 CLAUDE.md）
.agent/directives/「這條規範的完整版？」被指標引用時短到可以直接寫進 CLAUDE.md 的規則
memory/MEMORY.md「有哪些長期記憶？」每個 session記憶的內容——只放一行指標
memory/feedback_*.md「使用者要我怎麼工作？」相關時召回程式碼結構（那會過期）
.claude/agents/「誰去做這種審查？」被分派時需要寫入權限的任務
tests/「這條規則有沒有被違反？」CI／每次建置—（能寫成測試的都該寫）
最容易搞混的一組：CHANGELOG vs .develop CHANGELOG 是給使用者看的結果——「新增了什麼、修好了什麼」。 .develop/ 是給未來的自己（和 AI）看的過程——為什麼選這個方案、否決了哪些、 當初踩到什麼坑。前者一行，後者可以是三千字。兩者混寫會讓 CHANGELOG 變成沒人讀的長文。
05 — 工作流資料夾

.develop/：把狀態寫在資料夾名字上

這是整套結構裡最容易複製到別的專案、也最立即見效的一招。 命名格式固定為 YYYY-MM-DD_[主題]_[版本]_[狀態]/，四個欄位各有存在理由。

欄位範例為什麼是這樣
YYYY-MM-DD2026-07-30開工日，不是完工日——狀態改名時保持穩定。日期在前是因為版本字串字典序會排錯（v0.10 < v0.2）
主題DBG-023_transfer-order里程碑名、除錯編號、或決策主題。ls 就是一份可讀的專案史
版本v0.18.0 / vUnreleased對應 CHANGELOG 的版本區段，把「過程」與「結果」串起來
狀態TODO / CHECKing / DONE必填。不需要開任何檔案就知道整個專案還有幾件事沒做完

生命週期：只有兩次改名

TODO
規劃時建立。至少要有一份計畫。此時還沒動任何程式碼。
plan.md + plan.html
CHECKing
開始實作時git mv 改名。過程中補進驗證報告、截圖、完成草稿。
+ verify-*.md, *.png
DONE
程式碼已合併、檢查清單跑完，才改到 DONE。同時把 vUnreleased 換成真實版本號。
+ completion.md
為什麼用改名而不是移到子資料夾 git mv 改名保留完整歷史，而且路徑變動一眼可見於 diff。 更重要的是：狀態與內容不會分離——不會出現「資料夾在 completed/ 但裡面寫著待辦」這種漂移。 代價是引用該路徑的連結需要一併更新，這一步明文列進了任務後檢查清單。

除錯案例：把一次痛苦變成一份資產

除錯案例（DBG）用同一套命名，平放在 .develop/ 根層，另有一份索引。 每案固定六段：症狀 / 根因 / 失敗過的嘗試 / 修法 / 驗證方式 / 教訓。 「失敗過的嘗試」這段常被省略，但它其實是最值錢的——它阻止下一個人重走同一條死路。

開案門檻寫死在索引裡，避免變成流水帳：停線級別、診斷超過一小時、 同類問題復發、客戶可見、或跨模組——五取一才開案。

06 — 自動化層

Skills、Commands、Agents、Workflows 的差別

這四種東西長得很像（都是資料夾裡放 Markdown），但觸發方式與用途完全不同。 選錯種類是常見的浪費：把該自動觸發的寫成手動指令，等於沒寫。

種類怎麼被觸發適合放什麼本例
Skill 自動——模型讀 description 判斷相關性後主動載入 「遇到這類任務就該照這個流程做」的工作方法 CRM 復刻流程：強制先截圖再寫規格
Command 手動——使用者輸入 /名稱 使用者自己決定何時要跑的整套流程 /review-all、/audit-prerelease
Agent 被分派——主對話把子任務丟給它，獨立 context 大量讀檔但只需回報結論的工作（審查、稽核、搜尋） 6 個唯讀審查代理，各自限定工具權限
Workflow 腳本編排——用程式控制多代理的分派與匯總 需要確定性控制流的大規模平行作業 5 個平行稽核 → 對抗式驗證 → 綜整報告
Hook 事件觸發——由執行環境在特定時機執行 不能依賴模型記得的強制動作 設定於 settings.json
子代理最被低估的價值：context 隔離 一個「掃過 200 個檔案找出所有重複常數」的任務，如果在主對話做，200 份檔案內容會永久佔住 context。 交給子代理做，主對話只收到一份結論。會讀很多、但只需要回報結論的工作，一律外包。

把規則變成會亮紅燈的東西

本專案最有效的一次結構改良，不是新增文件，而是新增一支測試：它掃描所有領域實體的公開方法， 斷言每一個都真的被應用層引用過。這抓出了一整族「功能寫好了但使用者根本點不到」的缺陷—— 這類缺陷可以靜默存在數個月，因為單元測試全部是綠的。

判準　同一類錯誤犯第二次，就不要再寫進文件了——寫成測試、hook 或 lint 規則。 文件靠人記得，機制不需要。
07 — 記憶層

索引與內容分離：MEMORY.md 模式

長期記憶最大的風險是「越記越多，最後每次對話有一半在讀舊筆記」。 解法是把索引和內容拆開：索引常駐、內容按需。

MEMORY.md ＝ 目錄

一則記憶一行：標題、連結、一句鉤子。永遠不放內容。 現在 115 行涵蓋 66 則記憶，每次對話只花這 115 行。

單檔 ＝ 一則事實

一個檔案只講一件事，檔名即語意（feedback_ / project_ / reference_）。 用 [[連結]] 互相指涉，形成可導覽的網。

定期壓縮

每次發版時把已完成項目從「詳述」壓成「一行指標」，指向 .develop/ 裡的正本。 只搬家，不刪除。

值得注意的是不該記什麼：程式碼結構（會過期，而且可以直接搜）、git 歷史（本來就在）、 只對單次對話有意義的東西。如果一則記憶會因為改了一行程式碼而變錯，那它就不該是記憶。

08 — 可搬走的規則

從零開始的 10 條

不必一次到位。下面依「投報率」排序，前三條就足以讓多數專案的 AI 協作品質明顯改變。

  1. 先寫專案根目錄的 CLAUDE.md，只寫三件事 怎麼建置、怎麼測試、有哪些不明顯的慣例。控制在 100 行以內。這一份的投報率遠高於其他所有努力。
  2. 建立任務資料夾，狀態寫在名字上 YYYY-MM-DD_主題_狀態/。第一個任務就開始用，成本近乎零，一個月後就會感謝自己。
  3. 凡是踩過兩次的坑，寫成 Lessons Learned 一行 放在專案 CLAUDE.md 底部。一行、具體、含錯誤徵狀關鍵字，讓下次搜得到。
  4. 子目錄超過 3 個架構分層時，往下拆 CLAUDE.md 判準是「這條規則只有動到這個資料夾時才需要知道」。拆下去，別讓根目錄的檔案膨脹。
  5. 長篇規範外部化，根檔只留一行指標 「詳見 .agent/directives/versioning.md」比把三百行貼進常駐檔好。指標要具體到檔名。
  6. 記憶區用索引＋單檔 索引常駐、內容按需。一檔一事實，檔名帶類型前綴。
  7. 會讀很多檔的工作交給子代理 審查、稽核、跨檔搜尋。主對話只收結論，不收檔案內容。
  8. 把重複踩到的規則升級成測試 文件會被忘記，紅燈不會。第二次犯同樣的錯就是升級的信號。
  9. 為索引檔設觸發規則 除錯案例、決策文件都要明訂「什麼情況才開新的」，否則索引會退化成流水帳而沒人讀。
  10. 明訂例外並寫進慣例本身 一定會有不符合規則的資料夾（如 _misc/）。與其假裝沒有，不如列出來—— 未列出的例外才是結構腐化的起點。
09 — 反模式

看起來很整齊，但會壞掉的做法

以下每一條都是實際發生過、然後被推翻重做的。

寫給不存在的執行環境

設計一整套旗標、角色、路由與評分機制，但沒有任何程式會解析它們。看起來很專業，實際上是純裝飾， 還持續佔用每次對話的 context。

改為　只寫執行環境真的會讀、或人真的會照做的規則。設定健檢時第一個問題永遠是「誰會執行這條？」
用狀態資料夾分類任務

active/、completed/、planning/ 這種佈局，在「東西被移動但內容沒更新」時會立刻漂移， 而且丟失日期與版本的關聯。

改為　狀態當成資料夾名稱的後綴，用 git mv 改名。狀態與內容永遠綁在一起。
一份大而全的 CLAUDE.md

超過 500 行以後，規則開始互相矛盾且沒人維護得動。而矛盾的規則，實務上等於沒有規則。

改為　分層拆分，並定義衝突時的優先序（越具體的層級越優先）。
把可搜尋的事實寫成文件

「本專案有 202 個實體、目錄結構如下…」這類內容會在下一次重構後變成假資訊， 而錯誤的地圖比沒有地圖更糟。

改為　只寫推導不出來的東西：慣例、決策理由、陷阱。結構讓工具去查。
記憶只增不減

每次對話都覺得「這個記一下」，半年後索引本身就吃掉大量 context，且新舊記憶互相矛盾。

改為　設定壓縮時機（如每次發版）；已完成的壓成一行指標；發現錯的直接刪掉。
規範與範本分離

規則寫著「輸出要符合某格式」，但沒有可複製的範本——結果每次產出的格式都不一樣，規則形同虛設。

改為　規則旁邊一定要有 templates/，並在規則裡寫明範本路徑。
最後一句 這套結構不是設計出來的，是撞出來的——每一條規則背後都有一次代價。 所以不要一次照抄，從第 1～3 條開始，等到真的痛了再加下一層。 過早的結構和沒有結構一樣糟，差別只在前者還額外浪費了維護成本。
